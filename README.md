# goron — 2軸クランク脚ロボット

胴体＋左右独立2脚（360°連続回転）で、起き上がり・移動・横転・ジャンプを
強化学習で獲得させるプロジェクト。MuJoCo でのシミュレーションと Sim2Real を前提とする。

参考: [poco](https://homemadegarbage.com/rl13)（2軸シリアルアーム型）。本機はシリアル
チェーンではなく **胴体＋左右独立脚のパラレル構造**で、脚が連続回転する点が異なる。
脚を矢状面で連続回転させる構成は [RHex](https://en.wikipedia.org/wiki/RHex) 系
（回転するCレッグ）の最小構成にあたる。

## 機体構成

```
        torso  (M5Stack + バッテリー, free joint)
       /                              \
   hip_left (hinge, axis = Y)   hip_right (hinge, axis = Y)
   360°連続回転                  360°連続回転
```

脚は胴体の左右（±Y）に取り付くが、**振れる向きは前後（矢状面）**。ヒンジ軸が
胴体の左右方向(Y)に平行なので、両脚がオールのように前後に回り続ける。

この選択が設計全体を規定する:

- 両脚を揃えて回すと**ピッチ**トルクが出る。起き上がりは横転ではなく
  **前転／後転（宙返り）**になる。
- 難易度を決める胴体寸法は `torso_width` ではなく **`torso_len` (X)**。
  胴体は前後の端（x = ±27 mm）を支点として越えていく必要がある。
- 左右のミラー関係が存在しない。両ヒップとも +Y 軸まわりに同じ向きに回るので、
  `ctrl = [+a, +a]` で同位相（ピッチ／ホップ）、`ctrl = [+a, -a]` で逆位相
  （ヨー／シザース）。
- ヒップは**胴体より外側**（`hip_y_gap`）に出す必要がある。そうしないと脚が
  胴体を通過できず360°回転が成立しない。`leg_clears_torso` で検査している。

## 実機構成

| 部品 | 型番 | 諸元 |
|---|---|---|
| サーボ×2 | Dynamixel **XL330-M288-T** | 288.4:1、停動 0.52 N·m / 無負荷 103 rpm (5V)、12bit絶対エンコーダ、18 g |
| コントローラ | **M5Stack Core** 系 | 54×54×16 mm、6軸IMU内蔵 |

合計約 151 g。サーボは **Extended Position Control Mode（±256回転）** で駆動する。
このモードだけが「360°連続回転」と「絶対角度フィードバック」を同時に成立させる。

### 設計上の落とし穴（実装で踏んだもの）

**XL330のケース厚(26 mm)は M5Stack(16 mm)より厚い。** サーボを胴体の中央高さに
付けると、ケースが腹面より 5 mm 下に突き出し、ロボットは腹ではなく**サーボケースの上に
乗って静止する**。この状態では「腹が接地」というゴール条件が原理的に達成できず、
ゴール到達可能なクランク角は 24通り中 2通りしかなかった。サーボを上面側
(`hip_z_frac=1.0`) に寄せると 19/24 に改善する。`servo_clears_belly` で検査し、
`train.py` は違反する設定を起動時に拒否する。

## ゴール姿勢の定義（パターンA:「伏せ」）

`SelfRight` タスクは次の3条件が `hold_steps`（既定 25 step = 0.5 s）連続で成立したら成功:

1. 胴体の上向き軸が鉛直から `prone_tilt`（既定 25°）以内
2. **胴体の箱が床に接触している**（脚やサーボで突っ張っているのではない）
3. 角速度 |ω| が `settle_omega`（既定 3.0 rad/s）未満

2番目の接触条件が本質的。これがないと「脚で突っ張って斜めに静止」が成功扱いになる。
1番目は「横倒し／エッジ立ち」を排除する。脚は連続回転するので、伏せるにはクランクを
上向きに畳む必要があり、自然に「脚をたたむ」動作が要求される。

## 観測と行動（実機で取れる量だけ）

観測 14次元 — すべて M5Stack の6軸IMU と XL330 の TTL フィードバックから得られる:

| index | 内容 | 実機での取得元 |
|---|---|---|
| 0:3 | 重力方向（胴体座標系） | IMU 姿勢フィルタ / 加速度計 |
| 3:6 | 角速度 (rad/s) | ジャイロ |
| 6:10 | 各クランク角の sin/cos | XL330 絶対エンコーダ |
| 10:12 | クランク角速度（正規化） | XL330 Present Velocity |
| 12:14 | サーボトルク（正規化） | XL330 Present Current |

クランク角を生の角度ではなく **sin/cos** で入れているのは、関節が回り続けるため。
生角度だと1周ごとに不連続になり、値も無限に増える。

意図的に**含めない**もの: 胴体の位置とヨー角。実機で測れないし、どのタスクにも不要。
ヨー・並進・1回転ぶんのラップに対する観測の不変性はテストで担保している。

行動 2次元 `[-1, 1]`: Extended Position 目標角の**増分**。行動が飽和したとき
ちょうどサーボの無負荷速度になるようスケールしてある。さらに目標角は実測角から
`max_lead`（既定 0.5 rad）以内に制限される — これがないと脚が引っかかったときに
目標角が無限に先走り（ワインドアップ）、復帰に数秒かかる。実機でも必要なガード。

制御周期 50 Hz（物理 500 Hz、`frame_skip=10`）。

## タスク

ハードウェアは固定で、目的だけ差し替える。`Task` が持つのは
`reset()` / `reward()` / `terminated()` の3つだけで、観測・サーボモデル・接触判定は
`GoronEnv` 側にある。

| タスク | 内容 | 状態 |
|---|---|---|
| `selfright` | 仰向け → 伏せ | 調整済み |
| `forward` | 進行方向へ移動（RHex的なパドリング） | 初版 |
| `roll` | 横方向へ転がり続ける | 初版・意図的に難しい（矢状クランクはロールを直接作れない） |
| `jump` | 全体を浮かせる | 初版 |

`forward` / `roll` / `jump` は報酬項を素直に書いた初版で、ここから詰めるのが次の作業。

## セットアップと使い方

```bash
uv sync
uv run pytest tests/ -q

# MJCF を models/ に書き出す（閲覧用。学習側はこのファイルを読まない）
uv run python -m goron.model
uv run python -m mujoco.viewer --mjcf=models/goron_sagittal_bar.xml

# 設計解析: 越えるべき傾斜角と、開ループでの成功率
uv run python -m scripts.feasibility

# 設計スイープ: 脚形状・ヒップ位置ごとの成功率
uv run python -m scripts.basin

# 学習済み方策がどこで壊れるかを1軸ずつ探る
uv run python -m scripts.stress --run runs/selfright

# 学習
uv run python -m goron.train --task selfright --timesteps 2000000
uv run python -m goron.train --task forward --leg-shape c_leg

# 評価 + 動画
uv run python -m goron.eval --run runs/selfright --episodes 50 --video sr.mp4
```

## RL の前にやる設計解析

`scripts/feasibility.py` と `scripts/basin.py` は、**報酬設計をいじる前に機体形状が
解ける形になっているかを確認する**ためのもの。

- `flip_ladder()` — 胴体断面を「角で転がる長方形」とみなして、
  伏せ(0°) → エッジ立ち(90°) → 仰向け(180°) の間の不安定平衡点を出す。
  現行形状では仰向けから脱出するのに **106.5° を下回る**必要がある。
- `basin.py` — ランダムな開ループ行動列のうち何%がタスクのゴール判定を満たすかを測る。

**成功率**を見るのが重要で、「1回でも成功したか」では意味がない。開発中、可動域を
制限していた旧設計で見つけた唯一の成功シーケンスは、初期速度に 1e-4 rad/s の
ノイズを乗せただけで 0/10 に崩壊した。接触が支配的な系ではカオス的な"まぐれ当たり"が
出るので、方策が再現できる幅のある解でなければ意味がない。

参考値（既定形状、`selfright`）:

| 方策 | 結果 |
|---|---|
| 無動作 | 最終 tilt 155.6°（起き上がれない） |
| ランダム行動（毎ステップ） | 0/60 成功 |
| ランダム開ループ（0.4秒保持の区分定数） | 34.3% 成功 |

無動作では復帰せず、区分定数のランダム行動には広い成功領域がある — PPO にとって
適切な難易度。

## 学習結果（selfright, bar脚 50mm）

PPO 2M ステップ。**評価100エピソードで成功率100%、所要 0.8 秒**（うち 0.5 秒は
必須の保持時間なので、実際の起き上がり動作は約 0.3 秒）。20k ステップ時点で既に
100% に達し、以降 2M まで一度も崩れない。

学習した戦略は**クランク0.34回転（約124°）の単発の押し起こし**で、360°連続回転を
使い切ってはいない。起き上がりだけなら130°程度の可動域で足りる、ということでもある。

### 報酬ハッキングの記録

最初の実装では、成功でエピソードが終了する一方で成功ボーナスが定額 +100 だった。
ゴールに留まれば 3.0/step × 残り約380step ≈ 1150 得られるので、**サボる方が10倍
儲かる**。PPO は正しくこれを最適化し、伏せ姿勢に到達した上で1〜4ステップごとに
意図的にゴール条件を壊し続けた:

```
at_goal: 000000000000000111111110101110101111010111001110101111010111...
連続長:  [8, 1, 3, 1, 4, 1, 3, 3, 1, 4, ...]   ← 成功には連続25が必要
報酬 193 → 1006 に増加、成功率 100% → 0% に低下
```

修正は成功時に**残りエピソード分を払い出す**こと。これで留まる価値と等しくなり、
労力と時間ペナルティの分だけ早く終える方が厳密に有利になる。
`test_success_is_never_worth_less_than_loitering_at_the_goal` が回帰を防いでいる。

### 頑健性（`scripts/stress.py`）

1軸ずつ壊れるまで振った結果。ドメインランダム化なしで学習した方策を使用。

| 軸 | 破綻点 | 公称値との比 |
|---|---|---|
| 床摩擦 | μ=0 でも 100% | 効かない |
| **サーボトルク** | 0.05 N·m で 60%、0.03 N·m で 0% | **約10倍の余裕**（0.52 N·m） |
| 総質量 | ×16 で 100%、×24 で 84% | 16倍の余裕 |
| ギヤ減衰 | ×16 で 100%、×32 で 80% | 16倍の余裕 |
| 観測ノイズ | σ=0.8 でも 100% | — |

ドメインランダム化あり/なしの評価はどちらも100%だった。ランダム化幅（トルク±20%等）が
破綻点から桁で離れているため差が出ない。**この課題はトルク臨界ではない**ので、
サーボモデルの誤差が Sim2Real を壊す心配は小さい。

観測を殺すと成功率が落ちる（ゼロ固定 40%、ランダム 44%、正常 100%）ので、
方策は開ループではなく観測を実際に使っている。それでも大きなノイズに耐えるのは、
ノイズが乗っても信号が期待値として残るため。
