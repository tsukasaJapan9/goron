00全体像 — 6つの工程と、戻る矢印

Sim2Real は一本道ではありません。実機で測った値がモデルに戻り、モデルが変われば方策を学習し直す。この往復が本体です。

題材にする機体

胴体（80×80×72 mm の箱に M5Stack とバッテリー）の左右に、360°連続回転する脚が1本ずつ。脚は矢状面（前後方向）にしか動きません。自由度は2つだけです。合計 303.9 g。

自由度が2つしかないので、できることは限られます。腹ばいで進む（crawl）、前転しながら進む（forward）、仰向けから起き上がる（selfright）。二足歩行はできません — 片脚を上げた瞬間に横方向の支持が点になり、ロール方向の自由度がないので復帰できないからです。この「できないことの見極め」も設計解析の一部です。

01MuJoCo をさわる

MuJoCo は物理エンジンです。ロボットと世界を XML で書き、それを読み込んで時間を進めます。

最小のモデル

まずは箱が落ちるだけのモデルです。これを hello.xml として保存します。

<mujoco>
  <!-- 物理の設定。timestep は 1 ステップの時間 -->
  <option timestep="0.002" gravity="0 0 -9.81"/>

  <worldbody>
    <!-- 床。plane は無限平面 -->
    <geom name="floor" type="plane" size="5 5 0.05"/>

    <!-- 箱。freejoint があると自由に動ける（無いと世界に溶接される） -->
    <body name="box" pos="0 0 0.5">
      <freejoint/>
      <geom type="box" size="0.05 0.05 0.05" mass="0.3"/>
    </body>
  </worldbody>
</mujoco>

ビューアで開きます。ドラッグで回転、ホイールでズーム。

uv run python -m mujoco.viewer --mjcf=hello.xml

Python から動かすときの最小形はこうです。この3行がすべての土台で、強化学習の環境も中身はこれの繰り返しです。

import mujoco

model = mujoco.MjModel.from_xml_path("hello.xml")  # 変わらないもの（形状・質量）
data  = mujoco.MjData(model)                       # 変わるもの（位置・速度・力）

for _ in range(1000):
    mujoco.mj_step(model, data)                    # 2 ms 進める
    print(data.qpos[2])                          # 箱の高さ
model と data の違いは最初に押さえる model は形と質量、data はいまの状態です。同じ model から data を何個も作れば、同じロボットを並列に何体も走らせられます。強化学習で12環境を同時に回せるのはこの構造のおかげです。

MJCF と URDF は別物

ロボットの記述形式には URDF（ROS 由来）と MJCF（MuJoCo 固有）があります。MuJoCo は URDF も読めますが、読めることと使えることは違います。

　URDFMJCF
書けるものロボット単体ロボット＋世界
床無いplane で定義
重力・タイムステップ無いoption で定義
アクチュエータ実質無いposition / motor など
接触パラメータ無いsolref / solimp / friction
ルートの扱い世界に溶接freejoint を明示

実務上は「URDF は CAD から質量・慣性を取り込む入口、MJCF は学習に使う本体」と分けるのが素直です。この題材でも、CAD の STL から慣性テンソルを積分した URDF を作り、学習用の MJCF はパラメトリックに生成しています。

freejoint を消すと自己衝突が始まる

症状
サーボ同定のために胴体を固定しようと <freejoint> を消したら、脚が指令と逆向きに吹き飛んだ。
原因
ルートに関節が無いと、MuJoCo はその body を世界に融合する。MuJoCo の接触除外規則は「親子間は除外、ただし親が世界の場合を除く」なので、除外が効かなくなり、サーボの箱と脚のハブが押し合っていた。
見つけ方
data.ncon（接触の数）を見る。学習用モデルは 0 だったのに、細工したモデルでは 12 になっていた。おかしいと思ったらまず接触数を数える。

02ロボットをモデルにする

XML を手書きすると、寸法を変えるたびに全部書き直すことになります。Python で生成するのが実用的です。

寸法をデータクラスに追い出す

@dataclass(frozen=True)
class RobotParams:
    torso_len:    float = 0.080   # 前後（この機体では転がる方向）
    torso_width:  float = 0.080
    torso_height: float = 0.072
    hip_y_gap:    float = 0.012   # 胴体側面からヒップ軸までの張り出し
    servo_stall_torque: float = 0.52   # N·m
    servo_no_load_speed: float = 10.79 # rad/s

    @property
    def hip_y(self) -> float:
        """胴体中心からヒップ軸までの距離"""
        return self.torso_width / 2 + self.hip_y_gap

    @property
    def leg_clears_torso(self) -> bool:
        """脚が胴体の外側を通れるか。通れないと 360° 回転が成立しない"""
        return self.hip_y > self.torso_width / 2 + self.leg_radius

def build_mjcf(p: RobotParams) -> str:
    return f"""<mujoco> ... size="{p.torso_len/2:.5f} ..." ... </mujoco>"""

こうしておくと、寸法のスイープも、実測値の反映も、1箇所を変えるだけで済みます。さらに leg_clears_torso のような成立条件をプロパティとして書いておき、学習の起動時に検査すると、「そもそも動けない機体で何時間も学習していた」を防げます。

衝突形状はビジュアルと同じにしない

ここが初心者のいちばんの落とし穴です。MuJoCo はメッシュを凸包として当てます。

指針 当たり判定は「見た目に似せる」のではなく「接触の性質を保つ」ように作ります。箱や円柱で足りるなら、その方が速くて安定します。凸でない形が本質なら、凸分解します。

03強化学習とは — 観測・行動・報酬

やることは1つです。観測を受け取って行動を返す関数を、報酬の合計が最大になるように調整する。それだけです。

観測は「実機で測れる量」だけで組む

これが Sim2Real の最重要ルールです。シミュレータでは何でも読めますが、実機で読めない値を観測に入れた瞬間、その方策は実機に載りません。

index内容実機での取得元
0:3重力方向（胴体座標系）IMU 加速度計
3:6角速度 rad/sIMU ジャイロ
6:10sin(qL), sin(qR), cos(qL), cos(qR)サーボの絶対エンコーダ
10:12クランク角速度（正規化）サーボの速度フィードバック
12:14サーボトルク（正規化）サーボの電流

意図的に入れていないものがあります。胴体の位置とヨー角です。実機では測れないうえ、どのタスクにも不要だからです。

角度を sin/cos で入れているのにも理由があります。この関節は回り続けるので、生の角度だと 1周ごとに不連続になり、値も無限に増えます。sin/cos なら連続で、有界です。

行動は「増分」にして、先走りを止める

# 目標角を増分で動かし、実測角から max_lead 以内に制限する
self.targets = np.clip(
    self.targets + action * self.max_delta,   # 飽和時に無負荷速度になるスケール
    angle - self.max_lead,                    # ← これが無いと壊れる
    angle + self.max_lead,
)

この clip は飾りではありません。無いと脚が引っかかったときに目標角が無限に先走り、障害が外れても数秒間あらぬ方向へ回り続けます（ワインドアップ）。実機でも必要なガードです。

報酬ハッキングは「起きるもの」として設計する

強化学習は報酬を最大化します。あなたが意図したことではなく、書いたことを最大化します。この題材でも2回起きました。

成功するとエピソードが終わるので、成功しない方が儲かる

症状
報酬が 193 → 1006 に増えたのに、成功率が 100% → 0% に落ちた。
原因
成功ボーナスが定額 +100 で、成功するとエピソードが終わる。一方ゴール姿勢に留まれば 3.0/step × 残り380step ≈ 1150 もらえる。サボる方が10倍儲かる。方策はゴールに到達した上で、1〜4ステップごとにわざとゴール条件を壊し続けた。
見つけ方
報酬と成功率を別々に記録していたから気づけた。報酬だけ見ていたら「うまく学習できている」と誤読していた。

修正は「成功時に残りエピソード分を払い出す」ことでした。これで留まる価値と等しくなり、労力と時間のペナルティのぶん、早く終える方が厳密に有利になります。

「立っている」を1ステップずつ払うと、立たずに寄りかかる

症状
「立つ」タスクで報酬が 463 → 4418 に伸びたのに、成功率（2秒連続で立つ）は最初から最後まで 0%。
原因
報酬に「姿勢の直立度」の項があり、そこから大半が入っていた。方策は胴体の角を床につけ、脚を下に折り込んで寄りかかる静的に安定な姿勢を発見。倒立振子を制御する必要がなく、報酬はほぼ満額。
見つけ方
報酬の内訳を項ごとに分解して、どの項から入っているかを見た。動画で姿勢を確認したら一目瞭然だった。

修正は高さそのものに、二乗で払うことです。寄りかかり姿勢は 48 mm、立位は 80 mm。線形だと 48 mm でも3割入りますが、二乗にすると1割以下に落ちます。

報酬設計の経験則 「望ましい状態」にフラグで払うと、フラグの境界を跨ぐ細かい振動で稼がれます。物理量そのもの（高さ、距離）に払うと、抜け道が減ります。それでも抜けられるときは、報酬ではなく構造で塞ぎます（例：転倒したらエピソードを終了する）。

04学習を回す前にやる設計解析

報酬をいじる前に確かめることがあります。そもそもこの機体で解けるのか。

やり方は単純です。ランダムな開ループ行動（0.4秒ごとに乱数を選んで保持）を何百回か流し、タスクのゴール判定を満たす割合を見ます。

best = []
for ep in range(150):
    env.reset(seed=int(rng.integers(1 << 30)))
    a = rng.uniform(-1, 1, 2)
    for step in range(env.task.max_steps):
        if step % 20 == 0:              # 0.4 秒ごとに選び直す
            a = rng.uniform(-1, 1, 2)
        _, _, term, trunc, info = env.step(a)
    best.append(info["best_held_s"])

「立つ」タスクで実際に出た結果です。

判定割合読み方
一度でも立てた99.3%立ち上がる動作自体は簡単。トルクは足りている
0.1 秒以上18.7%勾配がつながっている
0.5 秒以上0.0%保持は制御で解くべき部分
最長0.20 s倒立振子の時定数 88 ms の 2.3 倍

この分布が学習に投げてよいサインです。「一度も達成しない」なら報酬か機体が間違っています。「最初から100%」ならタスクが簡単すぎます。簡単な部分と難しい部分が分かれているのが理想です。

「1回でも成功したか」を見てはいけない 接触が支配的な系では、カオス的なまぐれ当たりが出ます。この題材でも、開発中に見つけた唯一の成功シーケンスは、初期速度に 1e-4 rad/s のノイズを乗せただけで 0/10 に崩壊しました。成功率で見てください。方策が再現できる幅のある解でなければ意味がありません。

05実機を測る — Sim2Real の本体

シミュレータの数字は、たいていデータシートか推定です。実機と合わせるには測るしかありません。何を測るべきかには順番があります。

この題材で、推定がどれだけ外れていたか

項目推定実測外れた理由
脚1本の質量20 g9 g印刷部品はスカスカ。体積×密度は過大評価
位置ゲイン kp5.00.673データシートから推定できない内部量
ローター慣性1.0e-82.26e-8コード中に「要実機同定」と書かれていた
乾性摩擦モデルに無し0.00877 N·m粘性減衰しか無く、項自体が欠けていた
床摩擦1.00.302既定値のまま

質量 — 秤で測る。ただし内訳に注意

脚が想定の半分以下だったのは、3Dプリント部品がスパースインフィルだからです。メッシュ体積 13.95 cm³ × PLA 1.24 g/cm³ = 17.3 g のはずが、実測 9 g。実効密度は 0.65 g/cm³ でした。

合計の誤差は2%しかありませんでしたが、脚の慣性は振り出しの力学を支配するので、こちらの方が効きます。慣性テンソルは CAD メッシュから積分できるので、実測するのは質量だけでよく、分布はメッシュに任せられます。

サーボ — ステップ応答を合わせ込む

最初は「電流からトルク定数を求めて物理定数を個別に同定」しようとして、行き詰まりました。

電流が立ち上がる前に脚が動き出す

症状
目標角を 25° / 60° / 120° と変えても、脚が静止している間の電流がどれも 180 mA 前後で同じだった。
原因
電流の立ち上がりに約 11 ms かかるのに、脚は 13 ms で動き出す。指令された電流に達する前に動き始めるので、静止中の値は制御ゲインの情報を持っていない。
見つけ方
ステップ幅を振って、静止中の電流が幅に比例するかを確かめた。比例しなかった時点で、この方法は使えないと分かった。

方針を変えました。物理定数を個別に同定するのをやめ、シミュレータの応答が実測の応答に合うようにパラメータを合わせ込む。sim2real で意味があるのは「目標角を動かしたとき脚がどう動くか」であって、内部の電流ではないからです。

def cost(x):
    kp, armature, damping, friction = np.exp(x)   # 正の量は対数で扱う
    m = build(kp, armature, damping, friction)
    err = [(simulate(m, step, t) - measured) / abs(step)
           for step, t, measured in runs]      # 10本の実測軌道
    return np.sqrt(np.mean(np.concatenate(err) ** 2))

res = minimize(cost, x0, method="Nelder-Mead")
同定でいちばん大事なのは「使わなかったデータで確かめる」 10本すべてでフィットして「よく合いました」は何も言っていません。片方の脚のデータをフィットから外しておき、そこで誤差を測る。これが過適合していないことの唯一の証拠になります。

摩擦 — 床を傾けられないときの測り方

教科書どおりなら、板に載せて傾け、滑り出す角度 θ から μ = tan θ です。しかし実際に走らせる床は傾けられません。本の表紙で測っても「PLA と本の表紙」の値が出るだけです。

そこで滑走減速法を使います。ロボットを床の上で手で押し、滑って止まるまでの加速度計を読みます。滑走中は水平方向に摩擦しか働かないので、加速度計が示す「見かけの上方向」が鉛直から atan(μ) だけ傾きます。傾斜台と数学的に同じで、板の代わりにロボットを滑らせるだけです。

回滑走時間傾きμ
1675 ms16.10°0.289
2403 ms17.09°0.307
3748 ms17.24°0.310
平均——0.302 ± 0.010

3回とも完全に同じ値が出たら、それは信号ではない

症状
最初の測定で 3回とも μ = 0.010 と完全一致した。
原因
2つ重なっていた。①ファームのバッファが 0.45 秒で埋まりきり、要求した3秒のうち滑走が記録に入っていなかった。②検出ロジックが「最も長く安定した区間」を探していたので、静止区間に引っかかっていた。
見つけ方
μ=0.01 は氷より滑る。物理的にあり得ない値だったので疑った。加えて、傾き 0.55° は加速度計のノイズ（σ≈0.5°）とほぼ同じだった。

教訓は2つあります。測定値がノイズフロアと同じ桁なら、それは測れていません。そして再現性が高すぎるのは、同じものを測り続けている疑いのサインです。直した後は 0.289 / 0.307 / 0.310 と、適度にばらつきました。

06座標系と規約 — いちばん時間を溶かす場所

物理パラメータより先に、どちらが前かで間違えます。しかも間違いが自己整合するので、検算をすり抜けます。

IMU の向きは3姿勢で決まる

静止した加速度計は「世界の上方向を、IMU の軸で表したもの」を返します。ということは、body 座標系での上方向が既知の姿勢で持てば、読み値がその body 軸を IMU 座標で書いたものそのものになります。2姿勢で2軸が決まり、3軸目は外積で決まります。3姿勢目は検算に使えます。

前後を取り違えると、左右も一緒に反転して、検算が通ってしまう

症状
較正した IMU 行列を入れたら、水平では正しいのにピッチとロールが両方逆になった。
原因
「鼻先を下に」という指示に対し、画面のある側を前だと思って姿勢を作った。この機体はモデルの +X が画面と反対を向く。前後が逆になれば左右も逆になるので、行列全体が Z 軸まわりに 180° 回っていた。
見つけ方
「水平は正しいのに傾けると両方逆」は Z 軸まわり 180° ズレの固有の症状。合成データで再現して確認した。3姿勢目の検算は通ってしまう — 2つの誤りが打ち消し合うため、この検算では検出できない。

教訓は「姿勢を言葉で指示するときは、機体の『前』ではなく、見える特徴で言う」ことです。この題材では以後「画面が上を向くように」と書き直しました。

関節の原点は、機械的に再現できる姿勢から取る

方策の観測には sin(q), cos(q) が入っています。つまり方策はクランクの絶対位相を見て「いま押すべきか」を判断している。実機のサーボの0度は「組立時にホーンがスプラインのどの歯に噛んだか」で決まる、脚の向きとは無関係な値です。ここがズレると方策は空を蹴ります。

最初は CAD 姿勢を目分量で作っていましたが、再現性がありません。「胴体を床に伏せ、両脚の先端が床に触れる姿勢」に変えました。手の感触で分かり、機械的に再現できます。この姿勢がモデル上どのクランク角に当たるかは計算で出せます（この機体では 279.6°）。

基準姿勢を選ぶときの条件 ①再現できる（機械的な当たりや接地で決まる）、②モデル上の角度を計算できる、③見分けがつく。この機体では床と交わる角度がもう1つ（62.1°）ありましたが、そちらは腕の途中が当たるだけで先端は浮くので基準になりません。計算で両方出して、条件を満たす方を選びました。

07実機に載せる

学習が終われば方策はただの行列積です。フレームワークは要りません。

重みを C のヘッダに書き出す

14 → 128 → 128 → 2 の全結合、活性化は tanh。これを配列と1つの関数として書き出します。マイコンには PyTorch も NumPy も要りません。

// raw_obs -> action。呼び出し側がメモリを持つ。動的確保なし
static inline void goron_policy(const float raw[GORON_OBS], float action[GORON_ACT]) {
  float x[GORON_OBS], h0[GORON_HID], h1[GORON_HID];
  for (int i = 0; i < GORON_OBS; ++i) {
    float v = (raw[i] - goron_obs_mean[i]) / goron_obs_std[i];   // 学習時と同じ正規化
    x[i] = v > GORON_OBS_CLIP ? GORON_OBS_CLIP : (v < -GORON_OBS_CLIP ? -GORON_OBS_CLIP : v);
  }
  // ... 3層の行列積と tanh ...
}
観測の正規化統計を一緒に書き出すのを忘れない 方策は正規化された観測で学習されています。平均と標準偏差（VecNormalize の統計）が無いチェックポイントは使えません。この題材では、最良時点の重みと最終時点の統計を組み合わせて評価してしまい、性能を5分の1に見誤ったことがあります。

書き出したら必ず元のフレームワークと突き合わせます。この題材では最大差 4.8e-07 でした。ここが合っていなければ、実機で何が起きても原因が切り分けられません。

50 Hz の制御ループ

実機側でやることは4つです。

  1. 観測を組み立てる（IMU を較正行列で回し、サーボから角度・速度・電流を読む）
  2. 方策を呼ぶ
  3. 行動を目標角の増分として積算し、実測角から MAX_LEAD 以内に制限する
  4. サーボに目標角を送る

描画と同じループに置くと制御周期が守れない

症状
50 Hz（20 ms 周期）で回しているつもりが、遅れが 51 ms に達していた。
原因
同じループで顔を描画していた。320×240 のスプライトを PSRAM から転送するのに数十 ms かかり、その間ループが止まる。
見つけ方
実測の周波数と1周期の処理時間を画面とログに出した。「50 Hz で回しているつもり」を数字にした瞬間に分かった。

直し方は、制御を別のコアの専用タスクに移すことです。ESP32 は2コアあるので、描画を Core 0、制御を Core 1 に分けます。

// Core1 で 50Hz を刻む。vTaskDelayUntil は周期の起点を保つので、
// 1回遅れても次で取り返し、平均周期がずれない
static void policyTask(void*) {
  const TickType_t period = pdMS_TO_TICKS(1000 / GORON_CONTROL_HZ);
  TickType_t last = xTaskGetTickCount();
  for (;;) {
    policyStepOnce();
    vTaskDelayUntil(&last, period);
  }
}
xTaskCreatePinnedToCore(policyTask, "policy", 8192, nullptr, 2, nullptr, 1);

動かす前に「空回し」する

いきなり方策にサーボを渡してはいけません。観測を組み立てて方策を呼ぶが、目標角は送らないモードを作ります。

O,up -0.02 +0.00 +1.00,  ← 伏せ・水平。IMU の軸マップが正しい
  w +0.01 -0.00 -0.01,   ← 静止。ジャイロの符号も妥当
  sc -0.20 +0.83 +0.98 +0.56,  ← クランク角が較正姿勢と一致
  v +0.000 +0.002, t +0.000,   ← 無回転・無負荷
  act +1.000 -1.000, 50Hz       ← 周期が出ている

これで観測の全項目・制御周期・方策の出力を、脚を一切動かさずに確認できます。ここが通ってから初めてトルクを入れます。

08デバッグの道具をつくる

Sim2Real の失敗は「どこが違うのか分からない」形で現れます。差分を見えるようにする道具に投資すると、後で全部回収できます。

実機をシミュレータに映す

いちばん効いた道具はこれでした。実機のテレメトリ（IMU と関節角）を PC で受け、MuJoCo の同じモデルに流し込んで描画する。物理は回さず、運動学だけ解きます（実機が正、画面が従う）。

data.qpos[base:base+3]   = [0, 0, height]
data.qpos[base+3:base+7] = quat_from_up(up)     # 加速度計から姿勢を復元
data.qpos[hip_l] = math.radians(crank_l)        # 実機のクランク角
data.qpos[hip_r] = math.radians(crank_r)
mujoco.mj_forward(model, data)                  # 運動学だけ。mj_step ではない
viewer.sync()

これで実機を手で動かすと画面のモデルが同じように動くようになります。左右の取り違え、原点のズレ、IMU の軸違い — 規約の間違いはすべてここで見つかりました。数字を睨んでいても分からないものが、並べた瞬間に分かります。

加速度計だけではヨーが復元できない 重力は鉛直軸まわりの回転に対して不変なので、機体を水平面内で回しても読みは変わりません。ヨーは原理的に復元できないので、ミラーでも回りません。これはバグではなく、実機の制約をそのまま表しています（だから観測にもヨーは入っていません）。

記録がないものは再現できない

学習を回すとき、寸法や質量をコマンドライン引数で渡していると、その値はどこにも残りません。この題材では、出荷済みの方策がどのロボットで学習されたのか分からなくなっていました。

さらに悪いのは、評価スクリプトがそれぞれ自分の既定値でロボットを組み直していたことです。方策を「学習したのと別の機体」で採点することが起こり得ました。

# 学習時に、ロボットと学習設定とコミットを丸ごと書き出す
payload = {
    "robot": params.to_dict(),
    "training": vars(args),
    "git_commit": subprocess.run(["git", "rev-parse", "HEAD"], ...).stdout.strip(),
}
(out / "params.json").write_text(json.dumps(payload, indent=2))

そして読み戻す側は、記録が無いときに黙って既定値へ落ちてはいけません。警告を出します。黙って落ちるのが、いちばん見つけにくい失敗の形だからです。

09残っている宿題 — 測れなかった値の扱い

この記事は成功譚ではありません。最後に載せた方策は実機で転びます。その理由が、Sim2Real でいちばん大事な教訓を含んでいます。

床の摩擦は測れました（腹を滑らせた 0.302）。しかし脚の摩擦は測れませんでした — 二本足では立たないので滑らせられません。そこで「腹も脚も同じ印刷 PLA が同じ床に触れるのだから同じ値だろう」と推論で 0.302 を置き、その値で学習し直しました。

シミュレータ上では新しい方策が勝ちました。同一シード100本の対応比較で +7.5%、統計的にも有意。ところが実機ではすぐ転びます。摩擦を振ってみると理由が分かります。

平均性能で選ぶと、脆い方策を選んでしまう

症状
シミュレータで有意に勝った方策が、実機では旧方策より明確に悪い。
原因
測れない量に対して一点で最適化した。そして選定基準を「その一点での平均性能」に置いた。μ=1.0 で報酬 12.4 に崩壊するのを見た時点で「汎化していない」と分かっていたのに、+7.5% を優先した。
見つけ方
実機で転んだ。シミュレータ上の比較では発見できなかった — 比較していた床が、学習した床と同じだったから。
測れない量があるときの正しい手順 ①その量をランダム化して学習する（不確かさの幅をカバーする）。②選定基準をピーク性能ではなく、想定範囲での最悪値にする。③図09のようなスイープを、実機に載せる前の必須チェックにする。

ドメインランダム化は「あれば良い」ではなく、測れない量が1つでもあるなら必須です。

10次に自分でやるときの手順

この題材で有効だった順番です。上から順に、前の工程が終わってから次に進みます。

  1. 実機で測れる量だけで観測を設計するここを間違えると、後の工程が全部無駄になります。位置とヨーは（測れないので）入れない。回り続ける関節は sin/cos で入れる。
  2. モデルをパラメトリックに書き、成立条件を検査にする寸法をデータクラスに追い出し、「脚が胴体を通れるか」のような条件をプロパティにして起動時に弾く。
  3. 当たり判定は接触の性質で決める凸包になることを忘れない。非凸が本質なら凸分解する。
  4. 学習の前に開ループで難易度を測る「一度も達成しない」なら報酬か機体が違う。「最初から100%」なら簡単すぎる。成功率で見る。
  5. 報酬は物理量に払い、抜け道は構造で塞ぐフラグに払うと境界の振動で稼がれる。報酬と成功率は必ず別々に記録する。
  6. 学習の設定を run に書き出す寸法・質量・コミットを params.json に。読み戻す側は、記録が無ければ黙らず警告する。
  7. 実機を測る。順番は 質量 → サーボ → 摩擦質量は秤、慣性は CAD メッシュから。サーボはステップ応答を合わせ込み、使わなかったデータで検証する。
  8. 座標系と原点を、実機とシミュレータを並べて確定するミラーを作る。姿勢は「前」ではなく見える特徴で指示する。原点は機械的に再現できる姿勢から取る。
  9. 測れなかった量はランダム化して学習するそして選定基準を、その量を振ったときの最悪値にする。
  10. 空回しで観測と周期を確認してから、トルクを入れる目標角を送らないモードで、観測の全項目と制御周期を確認する。

この10項目のうち、4・6・9 は今回の作業で「やっていなかったせいで痛い目を見た」項目です。順番に効いてくるので、面倒でも飛ばさない方が結局早いです。
